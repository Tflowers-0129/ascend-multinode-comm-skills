# 远端连接信息与现场建链排障指引

## 何时使用

启动前通信预检与建链失败排障是两个并列场景。本文第 1、2、4 节的连接信息、认证与定向读取边界供两者共用；第 3 节用于已发生故障的定位，第 5 节用于该场景的分析归档。预检按 [技能中的预检流程](../SKILL.md#启动前通信预检) 执行，不需要先找一份故障日志。

服务器可以有任意数量，角色/通信域来自真实或计划部署。这里的脚本是服务器上的文件，用户不必上传；工作目录与相对脚本路径默认在指定容器中解析，宿主 launcher 则明确标注宿主路径。只有真正缺失或歧义的信息才补问。使用所选 agent 当前实际可用的连接能力，不限定具体产品。

现场排障包括读取已有故障证据、检查实际运行状态，并按假设做必要的有界诊断。用户只请求排查时不修改配置、重启服务或占卡打流；需要新增测试进程/监听器或使用 NPU 时单独明确资源和授权。若用户明确“只读、不主动探测”，遵守其限制。仅要求完善技能/文档时不收集真实凭据、不连接历史服务器。

两种场景都先通过当前环境实际可用的 SSH、服务器连接工具或已建立的会话读取远端材料，不要求先把脚本转成本地审计目录。`audit_deployment.py` 仅是辅助静态分析器；`preflight.py` 用于受控探针，使用 `BatchMode=yes`，不实现交互密码登录。排障取证阶段不要直接运行完整 `inspect/check/pairs`，因为它可能初始化环境、选择测试网卡或创建测试进程；先保存失败现场，再决定需要测哪一层。预检则核实计划环境和测试资源后分阶段执行，不以“已经故障”为前提。

## 1. 引导用户提供连接信息

先整理用户已经给出的字段，只补问缺失信息；多台机器可用一张表。同一节点若有多个容器/部署入口，分别标注。不默认使用 root，也不按历史 IP 清单批量尝试连接。

| 信息 | 何时需要、如何提供 |
|---|---|
| 机器 IP / 主机名 / SSH 别名 | 每个目标必需，管理入口不等于 HCCL 业务 IP |
| SSH 端口 | 默认 22；自定义端口或 SSH 别名中的设置需明确 |
| 登录用户名 | 每个目标必需，或由已确认的 SSH 别名提供；普通只读账号即可 |
| 认证方式 | 已配置密钥/ssh-agent、密码、堡垒机或其他已有认证渠道 |
| 登录密码 | 仅密码认证时需要，由用户在安全凭据控件或自己的 SSH 终端输入；不填入聊天表格 |
| 密钥与口令 | 提供已配置的密钥别名或本地路径，不提供私钥正文；解密口令同样走安全输入 |
| 跳板机 / VPN / 堡垒机 | 如需，提供已有 SSH 别名、访问方式及目标映射；跳板机和目标机凭据分别处理 |
| 工作目录 / 部署脚本 | 如容器内 `/workspace/service` 和 `./deploy/start.sh`，也支持远端绝对脚本路径；必须保留启动时 cwd 语义 |
| 容器名与运行方式 | 宿主机 / Docker / 其他已有运行环境；不确定容器时可先列出现有容器供核对 |
| 容器内服务用户 | 已知时提供用户名/UID；预检从容器/启动配置核实计划用户，排障再对照实际进程；不把 SSH 用户等同于容器内用户 |
| 节点角色与实例关系 | 已知可提供，未知由脚本/可用进程发现；不强迫用户先整理完整 TP/DP/EP 清单 |
| 任务与服务状态 | 启动前预检，或当前建链失败；注明尚未启动、仍挂住或已退出。没有故障不必填写报错 |
| 检查 / 测试范围 | 围绕指定服务读取脚本、容器及网络/设备状态；主动测试所用空闲卡、端口与时间窗按需确认，不默认占用全部资源 |
| 日志 / 版本 | 已知可提供；预检没有故障日志不阻塞。版本先从当前容器/安装元数据发现；排障再从脚本重定向等定位日志 |

可直接向用户给出下面的填写模板，目标由本次信息填写，不预置地址：

```text
任务：启动前通信预检 / 当前建链失败排障（填写本次意图）
服务器列表：按实际数量逐项提供，每项配置可以不同
节点 node-a：
  IP / SSH 别名：填写本次目标
  SSH 端口：22
  用户名：audit
  认证方式：密码（也可填写“已有 SSH 密钥/别名”）
  密码提供方式：我在自己的 SSH 终端输入，不在这里填写
  跳板机/VPN：无 / 已有访问别名
  容器：inference-worker（无则填“宿主机”）
  工作目录：/workspace/service（容器内）
  服务部署脚本：./deploy/start.sh（相对于上述目录）
  容器内服务用户：已知则填写，否则请现场核实
其余节点：按相同字段补充；若共用容器名/目录/脚本，可注明共用值及各节点差异
服务状态：尚未启动 / 建链失败 / 启动后挂住 / 已退出
现象与日志：排障时提供已知报错/时间/路径；未知请现场发现，预检无故障日志可不填
检查范围：上述服务的脚本、依赖配置、容器及网络/设备状态；排障时包括已有日志和实际进程
主动测试资源：允许的节点/空闲卡/端口/时间窗；未确定请先核实，不执行部署脚本
修改/重启/新增监听器/占卡测试：先说明必要性与影响，再由我确认
```

IP、用户名、目录可正常提供；密码和私钥不进入这份模板。凭据准备状态可以记录为“待安全输入/已准备”，不记录其值。

## 2. 安全完成认证

1. 优先使用用户已有 SSH 配置、密钥、ssh-agent 或服务器连接会话。检查可用能力后再告诉用户如何输入；不要捏造当前产品有“密码保险箱”或受保护输入控件。
2. 用户选择密码认证时，明确需要目标机登录密码，但让用户通过实际可用的受保护凭据渠道或自己的 SSH 终端无回显输入。若助手当前工具不能安全处理交互登录，停在认证准备阶段，让用户准备密钥/已认证会话，或选择脱敏文件上传作为备选；不把凭据障碍说成网络/HCCL 故障。
3. 不把密码写入 shell 参数、`sshpass -p`、脚本、环境配置、SSH URL、日志或报告；也不读取无关的本地密钥/凭据文件。不复用旧聊天里的密码，不跨目标试密码。若用户已经误贴明文，不复述或落盘，并提醒移至安全渠道，必要时更换。
4. 保留 SSH 主机身份校验。首次连接由用户从可信渠道核对指纹并完成信任配置；密钥变化时停止并核实，不设置 `StrictHostKeyChecking=no`，不删除 known_hosts 条目绕过校验。
5. 认证失败、权限不足或目标身份不符时停止该节点的采集，报告具体障碍。不自动改用 root、sudo、修改账号/SSH 配置、开启端口转发或开放防火墙。其他已经授权且可访问的节点可继续只读分析。

以下仅演示身份核验。先完成主机指纹确认，SSH_TARGET 填写本次确认的 user@host 或已有 SSH 别名，SSH_PORT 填写实际端口（不填使用标准 22）；缺少目标时直接提示，不连接任何默认主机。

```bash
# 已配置密钥/agent；失败不弹出密码提示。
ssh -T -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=8 -p "${SSH_PORT:-22}" "${SSH_TARGET:?请填写本次确认的SSH目标}" id

# 密码认证：仅在用户可亲自输入的安全交互终端运行；密码不是命令参数。
ssh -T -o BatchMode=no -o NumberOfPasswordPrompts=1 -o StrictHostKeyChecking=yes -o ConnectTimeout=8 -p "${SSH_PORT:-22}" "${SSH_TARGET:?请填写本次确认的SSH目标}" id
```

`BatchMode=yes` 会禁用密码提示；不能在仍使用该选项时声称可以接受密码。一次身份核验成功也不意味着另一个 SSH 客户端/进程自动复用认证，应确认助手实际使用的会话可访问。[OpenSSH 认证交互与主机校验说明](https://man.openbsd.org/ssh_config)

## 3. 先定位现有故障，不从静态扫描结果起步

### 3.1 各节点先确认执行上下文

按“SSH 目标 → 现有容器 ID → 服务用户 → 工作目录 → 远端脚本”核实。逐节点记录，而不是把某个节点的 cwd、IP、容器用户或导出变量复制到其他节点。相对脚本应解析为该节点容器内的 `工作目录/脚本路径`；宿主路径和容器挂载目标分列。若用户给出的是统一 launcher，继续追踪它实际调度的节点入口。

在已经登录、目标已确认的宿主会话中，可以使用如下只读命令形态（示例名称/目录/UID 必须替换为已核实值，不启动容器）：

```bash
docker inspect --format '{{.State.Status}} {{.State.Pid}}' inference-worker
docker exec --user 1000 --workdir /workspace/service inference-worker pwd
docker exec --user 1000 --workdir /workspace/service inference-worker ps -eo pid,ppid,uid,lstart,comm
```

`.State.Pid` 是容器初始进程的宿主 PID，不直接当成模型 worker PID；需要记录命名空间内外的对应关系。容器不存在、停止、paused、工作目录不存在或读权限不足时，报告真实状态，并继续读取可用的宿主日志/挂载元数据，不为了排障擅自启动它。

新 `docker exec` 进程不是原 worker：`--workdir` 指定命令 cwd，`--user` 指定执行用户；exec 默认继承的是容器创建时环境，服务脚本后续 export 的值不必在新 exec 中出现。实际 worker 的 cwd、argv 和必要通信环境应从该 worker 的可读进程信息及启动日志核对，读取前限定字段并脱敏。[Docker exec 工作目录、用户与环境说明](https://docs.docker.com/reference/cli/docker/container/exec/)

### 3.2 关联多节点日志，找到最后成功点与首个失败点

先查当前进程存活/退出状态、启动时刻，再从指定脚本的日志重定向或容器日志取得故障窗口。Docker 日志可以按 `--since/--until`、`--tail`、`--timestamps` 有界读取；先过滤秘密再呈现。不加无限 `-f` 或会附带额外环境信息的 `--details`；docker logs 为空时检查脚本实际写入的文件，不能得出“没有错误”。[Docker 日志选项](https://docs.docker.com/reference/cli/docker/container/logs/)

按任务/实例、rank、对端 IP、session/请求标识关联，而不只比较各机最后一行。记录时区及节点时钟差异，区分某节点先退出造成其他节点等待，与真正首发的建链失败。记录每个相关参与者“最后成功阶段 → 第一个失败/等待阶段”，阶段定义见 [通信矩阵](communication-stages.md)。

| 现场位置/证据 | 下一步在现场核实 | 不据此误判 |
|---|---|---|
| 尚未进入 store；路径、库加载、参数或进程启动失败 | 远端 cwd/脚本/挂载、版本、实际用户权限与 worker 是否存在 | 不能把尚未启动 worker 判成 HCCL 网络不通 |
| TCPStore 等待/解析卡住，或 master 端没有注册齐 | 每个参与 rank 的地址、world/rank、监听归属、容器 DNS/NSS；对端是否已因别因退出 | ESTABLISHED 不排除反向解析阻塞，SSH 通不代表 store 通 |
| store 已完成，Gloo peer 组失败 | 每个相关 peer 的实际 GLOO 网卡、公布地址、路由/回程和监听空间 | 不只验证 master，也不假定所有节点组成一个 Gloo 组 |
| HCCL init 或首次 collective 失败 | 先分 Host 建链、卡/设备通道、拓扑/版本/资源；核对具体 group/rank 和首个失败 API | 不把 level0:fullmesh 当物理拓扑证明，不以单个 errno 猜防火墙 |
| P/D 各自已就绪，KV 注册/搬运或池化访问失败 | 相应角色之间的 metadata、endpoint、布局、资源注册、动态会话和双方日志 | 不用普通 AllReduce 成功排除 KV/MC2 问题 |

对照 [历史坑位](failure-playbook.md) 形成可检验假设。不能只摘一个 HCCL 报错就跳去打流，也不能只发现脚本某行可疑就宣布它导致当前故障。

### 3.3 对照声明值与真实运行值

建立逐节点对照表：角色/通信组、容器 ID、工作目录、入口、进程 PID/用户、必要版本、实际网卡/IP、监听地址/端口、rank 及可见卡映射。检查脚本 export、命令前赋值、docker 环境边界、覆盖顺序与远端 source 内容；实际进程已退出就注明只能从历史日志和配置推断。

检查 Host 网络与设备网络时，读取现有状态并从当前 namespace 对指定 peer 做有界地址解析、源路由核查。查清 `HCCL_IF_IP`、`HCCL_SOCKET_IFNAME`、`GLOO_SOCKET_IFNAME`、master/DP/connector 的最终取值和消费方。日志里的所有 IP 不能都当作管理 IP；同端口在不同节点不自动冲突。

容器 `/etc/hccl_rootinfo.json`、`/etc/hixlep.json` 或目录入口、`route.conf` 的来源、内容类型、挂载与版本消费路径按 [拓扑与文件指南](topology-and-files.md) 核查；有现场证据才判配置不适用。直接查 npu-smi/已支持工具的只读设备状态与占用，不重置卡、不停止原 worker。

### 3.4 按通信关系选择最小验证

从失败 group 和日志选边：worker→store、Gloo peer、HCCL 子域中的相关 rank，或 P→D/计算→存储。记录每条边的发起方、接收方、目标 namespace、IP/端口及证据来源；节点数不是固定常量。不盲目对所有服务器运行全量两两测试，也不把只测一条边描述成整组通过。

- 首先使用已有日志/状态和有界 DNS/NSS、路由查询验证假设；显式只读任务不启动主动探测。
- 若具体业务 endpoint 已明确且其协议允许无负载连接，可做限次数、限超时的 TCP 建连/关闭验证，并记录源地址、耗时、拒绝/超时。不向未知协议、生产 store/Gloo/HCCL 端口发送自定义测试报文；对现有服务的影响不确定时先确认。
- 需要证明 store/Gloo 而不是 TCP 可达时，提出使用空闲测试端口、独立测试 rank 的最小复现。获得相应授权后，在同容器、已核实用户/cwd、匹配环境中运行；不接入生产通信组，不用仍被生产 worker 占用的端口。
- HCCL/逐卡/hccl_test 仅在原因指向该层且确认空闲卡、测试端口和时间窗后运行。先故障相关的最小 rank/卡集合，再按需要扩到实际组；逐卡 `pairs` 每次取两个节点只是隔离手段，不限制现场总节点数。[HCCL 测试方法](hccl-testing.md)
- 必须验证真实 KV/MC2 路径时使用版本匹配的适配器；未有适配器/资源时报告剩余缺口，而不是用 TCP 或 AllReduce 代替。

`preflight.py` 可在授权后用 `stages` 选择 CPU/store/HCCL 阶段，但 `check` 仍会执行 inventory、DNS 和测试 TCP；CPU 阶段也可能产生多进程，不能把它当只读命令。按现场关系制作最小配置，设置节点的 `container`、`workdir`、必要的 `container_user`，审阅 `env_scripts` 后才允许其为探针初始化环境，绝不把部署脚本作为 env_scripts。该工具可能显式选择/覆盖测试网卡：对照 `tested_environment` 与故障 worker 原值，不能把不同环境下探针成功解释成原配置没有问题。

现场分析不限定节点数量；当前 `preflight.py` 单次配置支持 2～64 节点，`pairs` 单次恰好两个节点。这是现有探针的范围，不是技能输入要求。超范围应分批取证、对故障边定向测试或实现匹配适配，分批结果不证明未覆盖的全局通信域。

### 3.5 给出诊断，按授权修复与复测

结论分为“已确认原因”“有证据支持但尚待验证的假设”“当前缺失的证据”，每项写出现场路径/行号或日志/进程证据、受影响的参与者及验证动作。列出已排除项和局限，不能只给用户一张让其自己执行的通用检查清单。

现有授权范围内还有能区分假设的查询时继续做；缺认证、关键事实、额外权限或需要影响服务的验证时，准确说明阻碍和所需动作。用户请求修改后才给对应文件打补丁、重启指定实例并按原失败阶段复测；更改前保留必要基线。仅修正脚本、测试进程成功或 SSH 成功，均不等于生产服务已恢复。

## 4. 定向读取的范围与证据质量

连接动作本身会产生 SSH 审计记录和短时查询进程；“只读”指不修改部署/系统配置、不运行用户服务，不承诺系统完全没有任何日志副作用。

先核对节点身份、有效登录用户、容器 ID/名称、脚本根目录及当前时间。只有入口路径不明时才在用户同意的目录内列候选文件，不扫描整个 `/`、home、模型权重目录或凭据目录。对路径做规范化、处理引用及 shell 转义，不把用户输入/远端文本直接拼接成可执行命令；符号链接越出约定目录时先询问。

| 证据 | 只读取得什么 | 需要避免什么 |
|---|---|---|
| 部署脚本 | 当前入口、source 的文件内容、Python launcher、hostfile、rank table、KV JSON；记录源路径和行号 | 不运行 `bash -x`、source、eval、项目 import，不执行从脚本复制出的命令 |
| 容器配置 | 指定容器的镜像标识、运行状态、NetworkMode、挂载来源/目标/读写属性 | 不输出完整 inspect/环境变量；不新建或启动容器，不全量导出容器文件系统 |
| 实际进程配置 | 仅所选服务的启动参数、工作目录与通信环境变量，先过滤凭据；启动前预检无 worker 时以计划配置为线索并注明尚未观察到运行值 | 不用完整 `ps eww`、`env` 或 `/proc/*/environ` 转储；无法安全过滤时保留未验证，不因尚未启动而判建链失败 |
| 文件依赖 | 只读跟踪业务依赖，区分宿主路径与容器路径；核查 rootinfo/hixlep 的类型、存在性、来源和实际引用 | 不把缺文件直接判成故障，不一律删除或补挂文件；外部依赖超范围先询问 |
| 日志 | 排障读取所选服务、指定时间窗的少量故障上下文并脱敏；预检可无故障日志 | 不跟随无限日志、不读取无关租户日志或全量生产请求，不为了制造日志而启动服务 |
| 现场网络快照 | 读取网卡/IP、路由、MTU、监听信息，与计划配置及可用进程状态对照 | 状态取证与主动验证分开记录；预检按技能预检流程、排障按 3.4 控制范围，不改路由、MTU 或防火墙 |

容器内读取只用已有运行容器和最小读取命令，明确这会产生短时 exec 进程；容器未运行或无权限就标记未采集，不为审计启动它。Docker inspect 可用 `--format` 限定输出字段；例如只查已指定容器的网络模式，避免完整 JSON 含敏感环境信息。[Docker inspect 官方说明](https://docs.docker.com/reference/cli/docker/inspect/)

读取优先有界：先元数据/文件清单，再逐个读取必要的小文本；为命令设超时、为文件和日志设体积/行数上限，截断须在报告中明确。输入可能含秘密，先通过可信的定向读取/脱敏步骤去除密码、token、代理认证、私钥等；不能做到时让用户提供脱敏片段，而不是把整个文件打印进工具输出。

不要为了“还原环境”主动执行 profile、CANN 初始化或业务 source；读取内容即可。若登录环境本身有启动钩子/受控命令限制导致无法可靠只读，记录限制并与用户协商读取方式。

## 5. 辅助脚本分析与报告归档

需要进一步还原脚本语义时读 [部署脚本分析规则](deployment-script-audit.md)，核对各节点入口、变量生效顺序、P/D/存储组、rank、端口和 connector 元数据。这是现场证据链的一部分，不替代上面的运行时定位。不同实例/角色不因同名文件而强行合并。

可以直接根据远端带行号的脱敏文本分析；需要静态工具时，把授权读取的必要文本保存到本地忽略目录（例如 `reports/remote-audit/<采集批次>/<节点>/`）。保留目录结构与原始行号，脱敏不能删行；保存节点、容器、远端绝对路径到本地路径的映射及采集时间。跨节点同名文件必须隔离，不能覆盖。

`audit_deployment.py` 不会把远端绝对 source 路径自动映射到本地快照，也不模拟所有远端 cwd。不要改写快照冒充原文件；这些依赖由助手按来源映射继续语义分析，或将已核实的通信参数写入本地审计 manifest 并标明证据来自现场/清单。原文、快照、凭据及报告不推送仓库。

最终报告至少列出：

- 已连接/未连接节点，容器身份、采集时间和实际读取范围；失败节点不补猜配置。
- 脚本声明与现场观察的对照，证据定位为“节点 / 容器 / 远端绝对路径:行号”；运行时查询注明来源与时刻。
- 确定错误、条件风险、缺失信息，分别给出触发条件、影响阶段和最小修改建议。
- 仍未验证的 TCPStore/Gloo/HCCL、逐卡、KV/MC2 与真实请求；只读审计不能产生这些项目的 PASS。

对只读任务始终维持只读；对故障排查任务，受控验证按 3.4 的资源/权限边界执行。记录每项实际执行的查询/测试、目标上下文与结果，未测项不填 PASS。

## 交付检查

连接信息未齐时提示补全，而不是硬连历史机器；选择密码认证时指向真实可用的安全输入方式；无主机信任/认证/读取权限时准确报告阻碍；可读节点继续分析。技能能够指导这一路径不等于该环境已经验证过 SSH、密码登录或 A5 通信。
