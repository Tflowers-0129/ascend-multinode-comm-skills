# 成功部署样本：少量代表案例比大量重复脚本更有用

成功脚本不是使用本技能、扩展 A3/A5 或开始预检的前置条件。它们主要帮助确认真实启动链、平台差异、变量来源与实际使用的通信分支。优先提供手头已有的代表案例，不要求先收齐一套平台×模式的完整矩阵。

## 选择哪些样本

| 优先覆盖的差异 | 希望回答的问题 |
|---|---|
| A3 与 A5 各自已有的成功案例 | 镜像/版本、卡映射、设备网络、容器资源有什么差异？ |
| PD 混部、PD 分离、池化 | 哪些组内通信、跨实例 KV/存储路径真正执行过？ |
| 不同 HCCS、RoCE、UB/UBoE 路径与拓扑 | 哪些是物理条件，哪些只是环境变量或算法设置？ |
| Dense、MoE、不同 MC2 和 eager/图模式 | 实际触发了哪个融合算子与资源初始化路径？ |
| 不同版本或“失败→修复→成功”的同一套部署 | 哪项变更解决了哪个阶段的问题，是否同时存在其他变更？ |

只换 IP、容器名但其他相同的脚本通常属于一个案例；不同规模仍可能改变通信算法或组网层级，若确有不同路径则另记。没有某模式成功样本就明确留空，不拿其他模式代替。不要故意破坏在线环境来制作失败案例。

## 用户怎么提供

默认提供远端位置，由 agent 使用当前实际可用的服务器连接能力读取；不要求先上传、下载或整理全部依赖。沿用 [连接信息与认证规则](remote-server-audit.md)，不要在聊天中提供密码/私钥。

```text
这是一个已成功运行的参考部署，请只读分析并提炼可复用检查项。
服务器列表：本次节点 IP/SSH 别名、用户名、端口、认证方式，按实际数量列出。
平台：已知则填写 A3/A5；未知请从现场识别。
各节点容器：xxx；工作目录：xxx；部署入口脚本：xxx（远端路径）。
成功运行时间：xxx；成功请求/日志路径：xxx；未知项请现场核实。
与当前故障/待预检部署的关系：同版本对照 / 另一平台 / 另一模式。
只读范围：上述服务入口、其必要依赖、版本、网络/设备与相关成功日志。
不要重跑脚本、启动服务、占卡或修改配置；需要扩大范围请先说明。
原始脚本和日志仅供本次分析，不自动推送仓库。
```

用户先给入口和已知信息即可。agent 在授权范围补齐：宿主 launcher、容器启动参数、source/env/config 链、P/D/store/router 各自入口、镜像 digest、驱动/CANN/torch_npu/vLLM-Ascend/connector 版本、并行组与卡映射；不扫描整个服务器，也不把环境中的密码或 token 收进报告。

“能成功部署”应分级记录：

- 脚本声称可用，或进程存活/health=200：候选样本，不是服务验收。
- 有实际请求成功与各必要节点日志：记录请求时间、结果摘要和路由，确认是否确实经过多节点/P→D。
- 声称 KV/池化/MC2 成功：分别需要远端 KV 读回/命中、存储操作、真实融合算子执行证据；普通请求成功不能证明所有可选分支都触发。
- 历史成功只证明当时的版本/环境；当前已变更或无法复核的部分标记未知，不重新执行在线服务来补证据。

## agent 如何转成技能与回归

1. 为每例记录来源节点/容器、远端文件路径与行号、文件摘要、运行时间和实际版本；原文留在受控位置，不入 Git。
2. 区分“脚本声明”“当前观察”“历史实测”“推断”；对照同组所有节点的真实生效配置，不以单份入口代表整套部署。
3. 提炼条件规则：适用平台/版本/模式/通信组 → 影响阶段 → 可观察的错误 → 最小验证 → 不适用范围。修复前后同时变化多项时不能强行归因。
4. 将规则加入相应平台、HCCL、MC2、KV 或脚本分析文档；可确定的语义制作无凭据、无现场地址的最小合成回归，复杂动态 shell 保持 agent 语义分析，不伪称静态工具已自动支持。
5. 征得内容发布授权后，只提交脱敏且必要的规则/合成样例/测试。允许维护技能仓库不等于允许公开或推送用户整套私有脚本、配置、模型信息和日志，即使仓库是私有的也一样。

下一轮选择尚未覆盖、且有条件验证的代表案例即可；不设置必须提供多少份脚本的门槛。
